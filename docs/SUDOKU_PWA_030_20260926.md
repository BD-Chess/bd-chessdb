# 8zSudoku PWA — engine 0.3.0 update

Date: 2026-09-26. Scope authorized by BD: publish the improved `/S/new/` engine and use it as the basis for `/S/PWA/`. The native application draft PR #26 is separate and unchanged.

## Implementation choice

The existing PWA is upgraded. Its installation identity (`id`, `start_url`, `scope`: `./`), standalone display, existing icons and `ai8SudokuNavigatorV020PWA` storage namespace are retained. The displayed application name is exactly **8zSudoku**.

The game is generated from `public/S/new/app.html`, whose engine 0.3.0 was published in GitHub commit `b2c15da6abe2c1b6fbd9dcd23140e0568981fce9`. The source SHA-256 and all resulting PWA asset hashes are recorded in `public/S/PWA/release.json`. Hashes identify the actual bytes; this document's source commit describes the initial update, not future builds.

`scripts/build-sudoku-pwa.cjs` performs a deterministic transformation:

- Retain the PWA storage prefix for game, statistics, consent and Human Trace data, keeping it isolated from LAB and CURRENT.
- Change two lane descriptions to identify the installable edition.
- Track pending session restoration and queued reviews, and expose a small synchronous `SudokuNavigator.flushForUpdate()` adapter.
- Keep the `navigator-core` engine script byte-identical to LAB.
- Normalize only trailing file whitespace to one final newline.

Existing saved games retain their schema and namespace. Restore rechecks puzzle uniqueness as in LAB. The storage adapter does not silently import LAB data or reset old PWA saves.

## Offline and update behavior

The worker installs seven local assets: wrapper, standalone game, PWA controller, manifest and three icons. It downloads and SHA-256 verifies the complete set before opening the new release cache. Failure or a content mismatch rejects installation and leaves the previous release available. If a same-release cache already exists, a failed cache write also preserves it; successful writes only contain hash-verified bytes from that same release.

Cache identity contains the deployment scope and a digest of the assets **and normalized worker runtime**. Changes to worker behavior therefore get a new cache identity even when game assets are unchanged. The generated release block is excluded from its own runtime digest, avoiding a circular hash.

The active worker serves its verified cached release immediately, including equivalent local asset requests with query strings. It does not combine an old cached wrapper with a newer network game. A missing cache entry can be repaired only with bytes matching that release. It handles only its explicit same-origin asset list; other Sudoku lanes, other apps, API requests and non-GET requests bypass it. Relative URLs support `/S/PWA/` and deployments beneath a path prefix.

Updates do not force an in-progress game to reload. The wrapper registers with `updateViaCache: 'none'`, checks on launch and on focus, visibility return or reconnection, and shows **Save & update** when a worker is waiting. Checks are throttled to at most one per 30 seconds.

On the user's update click, the game first flushes its pending save and reports the actual persistence result. It refuses while startup/session restoration, a queued review, a worker task, puzzle generation or AI animation is active. The queued-review counter covers the interval before its worker starts; old imported unfinished records do not permanently block updates. The user can finish an operation or pause the solver and retry. A storage failure does not activate the update or reload the page. There is no automatic export/download.

Only after successful persistence does the wrapper send `ACTIVATE_UPDATE`. Its own controller-change event checks and flushes again before reloading, covering new actions or storage failures during asynchronous activation. If that second gate fails, or if another window activates the update, this window shows **Save & reload** and continues displaying its current game until the user acts. Closing all old windows also permits the browser's normal waiting-worker activation.

Cleanup removes only older cache names belonging to the same scope. The first-release `8zsudoku-pwa-v1` cache is removed only if it contains this scope's exact `app.html` and every cached request belongs to this scope. Unrelated app and deployment caches survive. Service-worker cleanup never touches localStorage.

## Future LAB changes

PWA is a separately published snapshot of the verified LAB source. It does not automatically copy future LAB edits. After reviewing a future LAB update, regenerate and check the PWA before publishing:

```sh
node scripts/build-sudoku-pwa.cjs
node scripts/build-sudoku-pwa.cjs --check
npm ci --ignore-scripts --prefix tests/sudoku
NODE_PATH=./tests/sudoku/node_modules node --test tests/sudoku-pwa.test.cjs
SUDOKU_APP_LANE=PWA NODE_PATH=./tests/sudoku/node_modules node --test tests/sudoku-engine-ui.test.cjs
```

`--check` does not write files and fails if the generated app, worker release block or release manifest is stale. The script fails if expected source adapter anchors have changed, requiring an explicit review instead of silently building an incomplete adaptation. Keep the generated game, worker and manifest in the same Git commit. A changed release causes installed clients to receive the update notification once that commit is deployed and checked by their browser.

## Verification and boundaries

The independent real-worker UI suite passed **9/9** on the generated PWA: engine interaction, restored sessions, actual save/restore across the PWA namespace, localStorage failure, storage isolation, busy generation/restoration, immediate queued review, pending solve and active animation guards. The shared core has no PWA-specific implementation fork. Separate worker/shell tests cover offline caching, integrity failures, update consent, activation races and scope boundaries; their actual final run is recorded in the parent publication report.

Netlify deployment and public live verification are deferred under BD's instruction to ignore the deployment block until October 1. This change updates GitHub production source; it does not claim that the public deployment or already installed phones contain the new bytes yet. No Netlify configuration, native PR #26, signing setup, app-store submission, CURRENT game or historical archive was modified by the PWA build.

Physical iPhone installation, Safari storage eviction, operating-system background termination and offline Files/Share remain device acceptance checks. Node/jsdom worker tests do not establish those platform behaviors.
