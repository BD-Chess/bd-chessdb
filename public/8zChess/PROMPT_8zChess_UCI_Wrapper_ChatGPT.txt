We are building **8zChess**, a standalone UCI wrapper/proxy engine.

Core idea:
Arena.exe (or any UCI GUI) should see 8zChess as a normal chess engine.
8zChess itself will:
- speak UCI to the GUI
- launch and control one or more real engines underneath
- optionally query ChessDB.cn over HTTP
- collect candidate moves / evals / PVs
- apply our DCC governance / tie-break logic
- return a final `bestmove` back to the GUI

IMPORTANT:
We do NOT want to fork or modify Stockfish code.
8zChess must be a separate wrapper/proxy program.

==================================================
GOAL
==================================================

Build a **minimal but real v1 implementation** of 8zChess that:

1. Works as a UCI engine from the GUI’s perspective
2. Launches one or more local UCI engines from the same folder
3. Requests MultiPV candidate lines from those engines
4. Optionally queries ChessDB.cn as another candidate source
5. Applies a DCC-based tie-break / governance layer
6. Returns one final `bestmove`
7. Fails safely: if DCC or network logic fails, fall back to the best local engine move

==================================================
TARGET IMPLEMENTATION STYLE
==================================================

Language:
- Prefer **Python 3** first for speed of implementation
- Standard library only if possible
- No heavy dependencies
- Keep architecture clean and small
- Aim for something like 1-2 core files plus small helpers

Later we can port to Bun / Rust / C++ if needed.
For now: correctness, clarity, logging, and testability matter most.

==================================================
HIGH-LEVEL ARCHITECTURE
==================================================

GUI/UCI side:
Arena.exe  <->  8zChess.exe / python wrapper

Backend side:
8zChess  <->  one or more local UCI engines
8zChess  <->  optional ChessDB.cn REST API

Basic flow:
1. GUI sends `uci`, `isready`, `ucinewgame`, `position`, `go`, etc.
2. 8zChess forwards the relevant position/search commands to backend engines
3. Engines return `info ... multipv ... score ... pv ...`
4. 8zChess parses top candidate moves
5. Optional: 8zChess also queries ChessDB.cn for `queryall`, `query`, `queryscore`, or `querypv`
6. 8zChess merges candidates
7. DCC governance chooses the final move
8. 8zChess sends `bestmove ...` to the GUI

==================================================
CHESSDB INTEGRATION
==================================================

ChessDB.cn should be OPTIONAL and controlled by flags/options.

Relevant API capabilities:
- query all known moves
- query best/candidate moves
- query score
- query PV line

Implement this only as a lightweight optional source.
Do NOT make network access mandatory.

If ChessDB is unavailable, slow, or returns bad data:
- log it
- ignore it
- continue with local engines only

==================================================
LOCAL ENGINE HANDLING
==================================================

8zChess should be able to use engines found in the same folder or listed explicitly.

Minimum support:
- one primary engine (e.g. Stockfish)
- optional second engine (e.g. LCZero or another UCI engine)

Design this so more engines can be added later.

Each engine should have:
- path
- enabled/disabled
- multipv setting
- optional per-engine timeout / move budget

==================================================
UCI REQUIREMENTS

8zChess must correctly support at least:

==================================================
DCC GOVERNANCE — V1
==================================================

For v1, keep DCC narrow and safe.

Do NOT try to replace engine search.
Do NOT build a full chess engine.

Instead:
- gather top candidate moves from backend engines
- if one move is clearly best by eval, allow normal engine choice
- if top moves are near-equal (within threshold cp), apply DCC tie-break

DCC tie-break inputs can include:
- candidate move
- eval score
- PV line
- agreement across engines
- optional ChessDB support
- simple stability / consensus logic

V1 DCC decision spirit:
- prefer moves with stronger cross-source support
- prefer moves whose future line is more stable / less collapse-prone
- prefer consensus under ambiguity, not brute override everywhere

==================================================
MERGING SOURCES
==================================================

Support three modes:

1. local
- only local UCI engines

2. chessdb
- only ChessDB candidates (if user wants pure experiment)

3. hybrid
- combine local engines + ChessDB

In hybrid mode:
- merge candidate moves by UCI move key
- keep track of which sources support each move
- keep per-source eval/PV if available
- compute a simple consensus score

Do NOT do a naive weighted average only.
We want DCC-style governance:
- consensus
- stability
- tie-break under ambiguity

==================================================
FAIL-SAFE RULES
==================================================

If anything goes wrong:
- missing engine
- bad parse
- no ChessDB response
- no valid candidate set
- DCC exception

then:
- fall back to primary engine bestmove
- do not crash
- log the failure cleanly

8zChess must always behave like a robust engine from the GUI perspective.

This log is very important for debugging and later case studies.
